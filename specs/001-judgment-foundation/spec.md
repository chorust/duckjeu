## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对数据行取得可信的类型化判断结果 (Priority: P1)

分析人员在现有数据查询中对结构化市场状态或文本提出自然语言标准，取得概率，再使用常规查询进行筛选和分析。判断值代表模型判断，不代表已验证事实。

**Why this priority**: 这是项目最小价值闭环，也能暴露真实服务能力与本地模拟之间的差异。

**Independent Test**: 使用非敏感样例数据，分别通过可控模拟服务和真实服务完成概率判断并核对输入输出对应关系。

**Acceptance Scenarios**:

1. **Given** 包含文本、有限数值、布尔及内部空值的多行结构化状态，**When** 对每行查询同一标准的概率，**Then** 每个有效输入得到 [0,1] 内的有限数值，结果与对应输入一致。
2. **Given** 原始文本状态，**When** 提交判断，**Then** 服务收到未经改写的文本。
3. **Given** 内容相同但字段排列不同的结构化状态，**When** 提交判断，**Then** 两者的规范化状态一致，同时数值与文本、空值与缺失保持可区分。
4. **Given** 已配置并显式启用真实服务，**When** 对至少三行非敏感样例执行判断，**Then** 返回真实结果，记录实际服务、模型、行数、请求数与总耗时；模拟结果不能满足该场景。

### User Story 2 - 使用布尔值和限定类别完成分析 (Priority: P1)

分析人员希望把二元判断变成筛选条件，或把每行状态归入自己指定的一个类别。

**Why this priority**: 三种结果形式共同构成当前版本已经确定的产品范围。

**Independent Test**: 使用可控概率和标签响应，分别验证布尔转换与类别判断，无需依赖真实模型的随机输出。

**Acceptance Scenarios**:

1. **Given** 可控概率 0、0.49、0.5、1，**When** 取得布尔判断，**Then** 依次返回 false、false、true、true；不使用另一套二元判断语义。
2. **Given** 至少两个合法且互不重复的选项，**When** 查询类别，**Then** 只返回候选中的一个原始标签。
3. **Given** 返回候选以外标签或服务不支持所需判断类型，**When** 查询类别，**Then** 查询明确失败，不能自动替换标签或伪造能力。

### User Story 3 - 安全配置并诊断失败 (Priority: P1)

使用者能先离线验证，再显式启用真实调用；输入错误、网络失败和服务异常不能被误当成业务判断。

**Why this priority**: 无声失败会直接污染筛选和决策，隐含外发则会产生不可控的数据与费用风险。

**Independent Test**: 使用模拟服务产生超时、鉴权失败、无效结果，验证查询失败、错误脱敏和空值不触发调用。

**Acceptance Scenarios**:

1. **Given** 任一顶层必需参数为空值，**When** 执行判断，**Then** 该行返回空值且不发起请求；结构内部空字段仍作为状态内容保留。
2. **Given** 空白问题、非法选项或不支持的状态类型，**When** 执行判断，**Then** 查询报输入错误，该无效行不提交服务。
3. **Given** 超时、鉴权失败、响应过大、非有限或越界概率、响应数量或身份不匹配，**When** 接收结果，**Then** 查询明确失败，无静默重试，无默认概率、布尔或标签兜底。
4. **Given** 两个连接使用不同服务或模型设置，**When** 分别查询，**Then** 配置互不污染；真实调用须显式开启，错误信息不包含凭据与原始敏感状态。

### User Story 4 - 在既有契约上逐步扩展 (Priority: P2)

维护者希望未来增加批处理、缓存、其他服务和数据库时，保留当前使用者的基础判断语义与既有用例。

**Why this priority**: 当前就明确兼容性边界，避免后续扩展要求用户重写全部查询或改变判断含义。

**Independent Test**: 规划评审逐项说明各个后续里程碑会新增或替换哪些职责，并使用同一套基础契约场景验证模拟和真实服务的可替换性。

**Acceptance Scenarios**:

1. **Given** 相同的有效请求及可控响应，**When** 切换服务，**Then** 概率范围、布尔阈值、标签限制、空值与失败规则保持一致；不支持的能力明确失败。
2. **Given** 同一输入的多次出现及多个不同输入，**When** 对结果进行关联校验，**Then** 每个判断有独立关联身份，能检测未知、重复或缺失响应，不依赖返回顺序猜测归属。
3. **Given** 后续批处理、缓存、多服务、性能分析、其他数据库、集合判断和判断定义的演进要求，**When** 评审当前设计，**Then** 每项有明确职责边界、兼容性约束及延期范围，不要求本期提前实现这些能力。

### Edge Cases

- 空输入集：返回空结果，不调用服务。
- 混合有效行与顶层空值行：空值不外发，其他结果不得错位。
- 问题或选项为零长度或仅空白、选项不足两个、含空值或重复标签：输入错误。有效文本及标签不自动修剪或改写；重复按原标签精确比较。
- 状态文本允许为空字符串；它与顶层空值不同。
- 非有限数值、日期时间、嵌套结构等：最小支持集外须经显式验证并文档化才可接收，否则明确报错。
- 响应错序、缺失、重复或未知关联身份：可正确关联才可写回，歧义或不完整响应必须失败。
- 查询中途失败：查询报错；已经发生的外部请求和费用无法回滚，不能宣称事务回滚撤销外部调用。
- 优化或重复执行可能导致额外调用：不承诺结果行数等于请求数；过滤效果以实际执行与调用记录为准。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 使用者 MUST 能从表或 Parquet 数据对逐行结构化或文本状态取得概率、布尔与限定类别三种结果。精确公开契约以根规格第 2 节为准，参数顺序和既有示例必须保留。（场景 1、2）
- **FR-002**: 结构化状态 MUST 稳定规范化，按字段名称排序，保留类型与内部空值，区分空值和缺失；最小支持文本、有限数值、布尔和空值。文本状态 MUST 保留原文。（场景 1.2–1.3）
- **FR-003**: 顶层必需参数为空值 MUST 返回空值且不调用服务；空数据集 MUST 不调用服务。（场景 3.1、边界）
- **FR-004**: 概率 MUST 为 [0,1] 内有限值；布尔 MUST 以同一二元概率的 0.5 为包含边界的真值阈值；类别 MUST 为给定候选之一，不把选项顺序或未知分数解释成置信度。（场景 1.1、2）
- **FR-005**: 空白标准或问题、非法选项与不支持类型 MUST 在提交该行前报错；不能用不可靠转换掩盖类型问题。（场景 3.2、边界）
- **FR-006**: 每个请求 MUST 可关联到原始输入位置；响应身份、数量、结果类型和值域 MUST 校验，任何歧义或缺失 MUST 明确失败。（场景 4.2、边界）
- **FR-007**: 超时、鉴权失败、无效响应、不支持的服务能力 MUST 使查询失败；MUST 有有限的调用超时和响应大小上限，MUST NOT 静默重试或伪造默认结果。（场景 2.3、3.3）
- **FR-008**: MUST 提供可控、可重复的离线模拟判断和一个经真实调用验证的服务；两者 MUST 遵循相同基础判断契约，分别验证概率和类别能力。（场景 1.4、4.1）
- **FR-009**: 服务、模型、地址和超时 MUST 按连接隔离；真实调用 MUST 显式开启；凭据 MUST 来自受保护来源，不能要求写入查询正文或输出日志，错误 MUST 隐去凭据和原始敏感状态。（场景 3.4）
- **FR-010**: 文档 MUST 说明模型判断的不确定性、数据外发、调用费用及可能重复执行；MUST NOT 承诺调用次数等于结果行数或默认具备业务校准能力。（场景 1、边界）
- **FR-011**: 交付 MUST 包含干净环境构建与加载说明、验证过的版本、非敏感样例、离线与真实演示以及可核验的结果类型、行数、请求数和耗时记录。（SC-001、SC-004）
- **FR-012**: 当前设计 MUST 分离宿主数据处理、判断语义、服务协议、执行策略与配置职责；后续扩展 MUST 能复用基础判断契约，具体设计约束见根规格第 9 节。（场景 4.3）
- **FR-013**: 当前交付 MUST 限于 v0.1；后续批处理、缓存、其他数据库及判断定义等仅纳入演进约束，不作为本期实现清单。（场景 4.3）

### Key Entities

- **状态（State）**：一行的原始文本或具有字段名、类型和值的结构化内容。
- **判断请求（Judgment Request）**：状态、问题类型、标准或问题、候选标签，以及独立关联身份；能够关联原始输入位置。
- **判断结果（Judgment Result）**：请求身份及经过校验的概率或标签；布尔是二元概率的阈值转换。
- **服务能力与上下文（Provider Context）**：服务和模型身份、支持的问题类型、连接级设置、受保护凭据来源。不同服务的分数意义不能未经验证视为相同。
- **验收记录（Acceptance Evidence）**：执行环境、服务与模型、样例、输出类型、行数、实际请求数、耗时和失败验证结果，不包含凭据或敏感原始状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一个文档明确支持的干净环境中，评审者依照说明无需修改源码即可完成安装加载和三个函数的离线示例，3/3 示例成功。
- **SC-002**: 基础契约样例对文本、结构化状态、顶层及内部空值、概率边界、阈值和合法类别的预期符合率为 100%；至少一个超过单批处理容量的混合数据样例无行错配。
- **SC-003**: 已列出的非法输入及服务失败场景全部被显式识别；空输入和顶层空值行调用数为零，错误输出中凭据与敏感状态泄漏数为零。
- **SC-004**: 至少一个真实服务完成三种判断形式的演示，每种至少三行非敏感输入，结果类型和行映射 100% 合法，并保留可复核的调用记录；无法访问真实服务时标为未验收。
- **SC-005**: 后续七类演进方向（批处理与缓存、多服务、性能分析、其他数据库、集合判断、判断定义、后续研究）在设计评审中 7/7 有对应职责、兼容性约束和本期边界；基础契约不会因切换服务而改变。

## Assumptions

- 根目录 spec.md 的现有 v0.1 功能与技术约束继续有效；本规格把它们组织成可验收需求，不扩大交付阶段。具体技术选型与模块设计由后续 plan 落实。
- 用户首先是能够编写数据查询的分析人员；本期不增加图形界面、账号体系或自动执行业务策略。
- 对“空问题/空选项”采用包含纯空白字符串的解释；选项列表中的空值非法，整个列表为空值则按顶层空值传播。
- 不额外制定缺乏依据的延迟或吞吐承诺；本期记录真实耗时与调用数，规模性能比较属于后续阶段。
- 真实服务协议、账号权限、可用模型与凭据是 live 验收依赖；规划时核实能力，不能将任意文本模型的自报数字默认等同于 JEV 概率。
- 当前 constitution 文件仍是未填写模板，不构成已批准项目原则；本次以用户指令、现有 spec 和 roadmap 为依据。
- 参考仓库只提供设计证据；采用代码之前须核对来源、许可证和兼容性。调研记录单独保存，不将未经验证的参考行为视为本项目契约。
